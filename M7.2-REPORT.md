# JPPC — Milestone M7.2: ELF fingerprint y traza MMIO dirigida

## Hallazgo crítico: identidad del xenon.elf

El ELF incluido en `src/pcp/TESTS/xenon.elf` tiene 425,492 bytes y contiene el banner:

`XeLL - Xenon linux loader second stage -git- 2012-10-26 (LibXenon.org)`

También contiene el encabezado `NEW LOG Patch v(1.035)`. No se encuentra como cadena ASCII literal el marcador indicado por el usuario:

`*Xenos FB with 148x41 (1280x720) at 0x9e000000 initialized.`

Tampoco aparece `XeLL Reloaded` como cadena ASCII literal. Esto no demuestra que el ASCII art no exista como datos gráficos, bitmap, datos comprimidos o construcción en runtime; sí demuestra que el ELF actualmente incluido no contiene el marcador textual literal y que es una compilación antigua identificable por su banner.

Por tanto, las pruebas previas no deben presentarse como validación del splash XeLL Reloaded que describe el usuario. Para una comparación inequívoca, el siguiente test de integración debe ejecutarse con el `xenon.elf` exacto que contiene el marcador de Xenos FB descrito.

## Cambios

- `pcp.utils.XenonElfAudit`: auditor read-only de identidad, SHA-256 y marcadores de build.
- `--bus-range INICIO:FIN`: permite limitar `--bus` a un rango MMIO sin saturar el log con accesos a RAM/framebuffer.
- El rango es inclusivo y hexadecimal, por ejemplo `--bus-range 0xEA001300:0xEA0013FF`.
- No se inventa estado de USB ni se fuerza la condición de espera a completarse. El controlador USB sigue pendiente.

## Ejecución

```sh
java -cp out pcp.utils.XenonElfAudit src/pcp/TESTS/xenon.elf
java -Xmx1g -cp out pcp.PCP src/pcp/TESTS/xenon.elf --elf \
  --size 1024x768 --tb 1000 --headless --bus-range 0xEA001300:0xEA0013FF \

```

## Evidencia de ejecución

SHA-256 del ELF incluido:

`851c9a7996ba84ee125279d144e4be9e274fe0995bf90711cfaabdd988da1866`

En la ejecución limitada a 300,000,000 instrucciones, el emulador llegó a 50,001,128 instrucciones y quedó en `PC=0x80008A70` (no halt). La traza filtrada del rango `0xEA001300–0xEA0013FF` registró:

- lectura de 32 bits en `0xEA001318`;
- escritura de 32 bits en `0xEA001318`;
- lectura de byte en `0xEA001307`;
- escritura de byte en `0xEA001306` con valor `0xE0`;
- escritura de byte en `0xEA001307` con valor `0xEC`;
- nueva lectura de byte en `0xEA001307`.

La última lectura retorna `0x00` porque el rango no tiene dispositivo asignado. El código PPC espera que los bits `0xC0` de ese byte sean `0x40`; al recibir cero, permanece en el bucle. Esto confirma una dependencia MMIO concreta, pero no identifica por sí solo la semántica del registro. No se debe responder `0x40` de forma artificial sin determinar el comportamiento del controlador.
