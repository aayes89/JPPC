# JPPC — Milestone M7.3: identificación y extracción del splash XeLL CP437

## Corrección del diagnóstico anterior

El `xenon.elf` incluido SÍ contiene el arte ASCII de XeLL. El logo está almacenado como bytes de texto de la página de códigos IBM CP437, no como ASCII de 7 bits. El auditor anterior buscaba únicamente las cadenas literales `XeLL Reloaded` y el mensaje de framebuffer, por lo que no detectaba el arte.

La atribución `Free60.org XeLL - Xenon Linux Loader -git-` aparece en el offset de archivo `0x5E641`. El bloque CP437 anterior se extrae desde el terminador NUL precedente hasta el final de esa atribución. La extracción es read-only y no altera el ELF.

## Identidad del ELF incluido

- Tamaño: 425,492 bytes.
- SHA-256: `851c9a7996ba84ee125279d144e4be9e274fe0995bf90711cfaabdd988da1866`.
- Banner de etapa: `XeLL - Xenon linux loader second stage -git- 2012-10-26 (LibXenon.org)`.
- Log: `NEW LOG Patch v(1.035)`.
- Atribución del logo: `Free60.org XeLL - Xenon Linux Loader -git-`.
- `XeLL Main Menu` está presente como cadena.
- El literal `Xenos FB with 148x41 (1280x720) at 0x9e000000 initialized.` NO está en este ELF como cadena ASCII.

La ausencia de ese mensaje literal no prueba que el modo no se inicialice: puede generarse dinámicamente o corresponder a otra revisión. El fragmento aportado por el usuario confirma el logo y las cadenas de XeLL 1.035.

## Cambios

- `XenonElfAudit` ahora reporta offsets de cadenas, detecta la atribución del logo y puede extraer el bloque CP437 mediante `--extract-logo`.
- `tests.sh` verifica detección, extracción y contenido del arte CP437.
- Se conserva el comportamiento read-only. No se incorporan CPU key, DVD key, fuse sets, KeyVault ni dump NAND al artefacto.

## Ejecución

```sh
java -cp out pcp.utils.XenonElfAudit src/pcp/TESTS/xenon.elf
java -cp out pcp.utils.XenonElfAudit src/pcp/TESTS/xenon.elf --extract-logo out/xell-logo-cp437.txt
```

## Estado de ejecución

La extracción confirma que el recurso del logo existe dentro del ELF. No confirma que la CPU llegue a imprimirlo. La ejecución anterior continúa bloqueada en `PC=0x80008A70`, esperando el bit `0x40` enmascarado por `0xC0` de `0xEA001307`; el registro sigue sin un controlador USB MMIO asignado.

No se ha simulado el bit de listo ni se ha declarado funcional EHCI/OHCI. El siguiente trabajo debe identificar el bloque USB al que pertenece `0xEA001300`, implementar la transición de estado esperada y comprobar si la ejecución avanza a las rutinas de framebuffer y menú.

## Alcance

M7.3 corrige la identificación del recurso visual y entrega una extracción CP437 reproducible. No entrega todavía el splash renderizado ni el menú funcional.
